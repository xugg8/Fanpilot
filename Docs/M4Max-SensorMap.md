### 2.1 三个必须知道的更正

1. **不存在 `F0Sd`**（原方案 P0 里列了这个键名）。
2. **不存在 `F0md`（小写）** —— 本机用大写 `F%dMd`；小写是 **M5** 的命名。
   → 键名必须**运行时探测**（先试 `F0Md` 再试 `F0md`），不维护芯片型号表。
3. **低温停转是正常状态**：`F0Tg = 0` 且 `F0Ac = 0` 表示风扇完全停转，
   UI 与告警必须区分"停转"与"故障"。

### 2.2 `Ftst`：M4 Max MacBook 的解锁闸门

- 本机 `Ftst` **存在**（ui8，值 0）。
- 风扇停转（低温闲置）时 `F0Md = 3`（Mode 3 / AppleCLPC 缓解态），
  此时**固件拒绝手动模式写入**（写 `F0Md=1` 后回读仍是 3，`result=0x82 SmcBadCommand`）。
- 解锁序列：**先写 `Ftst=1`**（让 `thermalmonitord` 松手）→ 等 0.5s → 在 10s 内以 0.1s 间隔
  重试 `F0Md=1`。**本机实测（冷机）：总耗时 3.0s，Ftst 后第 1 轮重试即成功**；
  热机直写路径仅 0.4s。
- ⚠️ **`F0Md = 0` 不代表锁已释放**：本机实测在 `F0Md` 读数为 0 时直写仍然失败
  （回读 0），必须回退 Ftst 分支。→ **不要用读数做分支优化，始终按两阶段尝试。**
- 恢复自动的顺序：**先把所有风扇模式写回，最后才关 `Ftst`**（它是全局闸门）。
- `Ftst≠1` 时系统会在数秒内 reclaim（空闲约 4000ms，**高负载可快到 250ms**）
  → 维持手动控制必须**常驻进程 + 周期重断言**。

## 3. 无效/固定读数键（**必须排除，否则风扇永久 100%**）

### 3.1 双相加热验证为"完全无响应"的 34 个键

在 GPU 负载（`Tp` +33°C、`Tg` +50°C）与内存带宽负载下**均无任何变化**：

```
TAOL TB0T TB1T TB2T TD00 TD01 TD02 TD04 TD10 TD12 TD14 TD22
TH0b TH0x TVA0 TVMD TVmd Ta01 Ta05 Ta09 Ta0L Ta0P Ta0S TaLT TaLW TaRT TaRW
Tf06 Tf16 Tf26 Tf36 Tf46 Ts0P Ts1P
```

其中 **`Tf06/16/26/36/46` 恒定在 97–116°C**（`Tf26`=116.12、`Tf16`=115.27、`Tf46`=107.31、
`Tf36`=104.17、`Tf06`=97.34）—— 这是**最危险的假传感器**：数值逼真、位置像热点，
一旦参与"取最大值"判据，风扇会被钉死在 100%，而日志看起来一切正常。

### 3.2 4 轮采样内完全不动、但需注意的慢变量（共 44 个 frozen）

电池/环境/板载类（`TB0T`–`TB2T`、`TD00`–`TD24`、`TDBP`、`TDVx`、`Ta01/05/09/0L/0P/0S`、
`TVA0`、`TVS0/1`、`TaRT`、`TAOL`、`Ts0P`）——**不是无效，而是热惯性大**，
可作背景参考，不应作为控制判据。

> 完整 44 项见 `smc-key-inventory.csv` 中 `class=frozen`。

|---|---|---|---|

| `Tpx1` / `Tp06` / `Tp0M` | ~63°C | 31.6–31.7°C | ❌ |
| `Tp02` / `Tp0I` / `Tp0Q` | ~58°C | 24–25°C | ❌ |
| `Tg*` 簇 | — | **6.7°C** | ✅ 相对稳定 |
| `TCMz` | 72.0°C | **0.92°C** | ✅ 稳定 |
| `TCMb` | 58.2°C | **0.66°C** | ✅ 稳定 |

## 5. 功率信号：`PDTR`（免 root，**前馈控制的主输入**）

| 键 | 实测值 | 含义 |
|---|---|---|
| `PDTR` | 闲置 **24–28**，10 核满载 **88–90**，**GPU 满载 118–136** | **系统直流总功率（W）** |
| `PHPS` | 15 → 22 → 66 | 疑似 SoC 功率分量 |
| `PDBR` / `P5SR` | 2.1 / 0.9 | 待定 |
| `VD0R` / `VP0R` / `ID0R` | 27.8 / 12.5 / 1.0 | 电压/电流 |

**响应速度**：负载启动后 **2 秒内** PDTR 即从 27W 跳到 85W；而温度要 16 秒才升到 112°C。
→ **功率比温度早 10–14 秒反映负载变化**，这是抢跑式控制的物理基础。

## 6. 差分负载指纹（P0 方法论 + 本机结果）

单次静态扫描无法区分"真传感器"与"无效键"。正确方法是**控制变量加热，看谁动**：

| 阶段 | 操作 | 用途 |
|---|---|---|
| 1 | 静置 25s | 基线 |
| 2 | **CPU-only** 满载 70s（10 线程） | 标出 CPU 簇 |
| 3 | 冷却 40s | 时间常数 |
| 4 | **GPU-only** 满载 70s（MPS matmul） | 标出 GPU / 供电簇 |
| 5 | 冷却 35s | — |
| 6 | **内存带宽型** 70s | 标出内存簇 |
| 7 | 判定 | 双相 Δ<2°C 的键 → 列入排除表 |

## 7. 关键动态实测

### 7.1 CPU-only 满载（10 线程，~88W）

| 时刻 | PDTR | Tp 峰值 | Tg 峰值 | 风扇目标 | 实际 RPM |
|---|---|---|---|---|---|
| 闲置 | 27.5W | 74.2°C | 55.4°C | 1350 | 1319 |
| +2s | **84.7W** | 96.0°C | 59.2°C | 1350 | 1355 |
| +8s | 86.7W | 101.2°C | 64.9°C | 1350 | 1380 |
| +14s | 88.1W | 106.2°C | 69.7°C | 1350 | 1340 |
| +16s | 89.9W | 108.2°C | 71.0°C | **1391** ← 才开始动 | 1345 |
| +24s | 88.1W | **112.3°C** | 75.5°C | **1749**（仅 30%） | 1702 |

### 7.2 GPU-only 满载（MPS，峰值 136W）

| 时刻 | PDTR | Tg | TVV（供电） | 风扇目标 | 实际 RPM |
|---|---|---|---|---|---|
| +5s | **135.9W** | 85.5 | 96.5 | 1350 | 1343 |
| +15s | 135.3W | 96.0 | 105.1 | 1350 | 1345 |
| +20s | 133.3W | 99.3 | 108.7 | 1514 | 1485 |
| +46s | 124.3W | 100.0 | **111.7** | 2686 | 2678 |
| +70s | 118.5W | 99 | 110 | 3235 | **3235（仅 56%）** |

**四个必须写进设计的事实**：
1. **Apple 的曲线极端滞后**：负载出现后**前 14–18 秒**风扇目标仍停在最低 1350 RPM。
2. **纯 CPU 满载就能到 112°C**（无需 GPU）→ "92°C 以下"不是调曲线的自然结果，**必须抢跑**。
3. **风扇跟随目标很快（滞后 ≲2–4s），慢的是 Apple 的决策** → 正解是**前馈阶跃**，不是纯 PID。
4. **风扇本身很快**：手动下发 4000 RPM 后 **2 秒内实际到 3891 RPM（≥1270 RPM/s）**。
   慢的始终是 Apple 的**决策**。→ 前馈抢跑完全来得及；"怠速地板"降级为可选优化项。
5. **Mode 3 锁的出现条件**：风扇停转（低温闲置）时 `F0Md=3`、固件拒绝手动写入；
   机器偏热（风扇在转、`F0Md=0`）时**直写 0.4s 即成功**。
   → 想给冷机"提前拉转速"（产品核心场景）**必然要过 Ftst 分支**。
6. **reclaim 有延迟**：3500 RPM 下 20 秒观测期**未发生**；1350 RPM 下 12 秒内未发生；
   进程退出后**数分钟**才回到 3。→ 不能依赖系统做及时恢复，但系统最终会兜底。
7. **3500 RPM 即可显著降温**：空闲 SoC 从 63–72°C 降到 **52–56°C**（仅上限的 61%）。

## 8. SMC 访问协议要点（全部实测，写库必须遵守）

1. **连接**：`IOServiceOpen("AppleSMC", 0)`，`IOConnectCallStructMethod(conn, 2, ...)`。
2. **缓冲区 80 字节，但不要用 Swift struct 镜像 C 结构体**：
   实测 `MemoryLayout<SMCKeyData>.size = 76`（C 是 80，Swift 尾部对齐规则不同）。
   → 用**显式 80 字节缓冲区 + 具名偏移**（`SMCKeyDataBuffer`）。
   偏移：`key@0`、`dataSize@28`(小端 u32)、`dataType@32`、`result@40`、`status@41`、
   `data8@42`(命令)、`data32@44`、`payload@48`(32 字节)。
3. **键总数**：命令 7 的返回写在 `[44:48]`，按 **大端** u32 解（本机 3386）。
4. **键名字段是主机序（小端）UInt32 fourcc，不是字符数组**：
   `"FNum"` 在内存里是 `6D 75 4E 46`（反的）。按字符顺序写 → 内核一律回 `result=0x84`（键不存在）。
   命令 8（按键索引取键名）的返回值同理。
5. **读值两步**：命令 9 取 `dataSize`/`dataType`；命令 5 读，且**必须预置 `dataSize = 32`**，
   否则 `result=0x89` 且无数据。`flt ` 载荷是**小端** float32。
6. **每键 dtype 不同**，必须按 `KEYINFO` 编码/解码：`flt `(4B 小端 float)、`sp78`(2B 大端 8.8 定点)、
   `ui8 `(1B)、`ui16`(2B)、`ui32`(4B)、`fpe2`(2B 大端 14.2 定点)、`hex_`、`flag`。
   > 踩坑：把 `ui8` 的 `F0Md` 当 float 写 4 字节 → 必然失败。
7. **写入（命令 6）三条铁律**：
   - **先查 `kern_return`**：非 root 时内核返回 `0xE00002C1 (kIOReturnNotPrivileged)`，
     而**输出缓冲区保持全 0**，于是 `result` 读作 `0x00`，**形似成功**。
   - **再回读校验，且回读必须带沉降窗口**：SMC 写入是**异步生效**的，
     写完立即回读拿到的是**旧值**（调研实测：`写 F0Tg=2500 → 立即读=1000 → 1s 后读=2500`）。
     策略：先查 kern_return，再在 6×200ms 窗口内确认回读。
   - 容忍 `result=0x87 (SmcKeySizeMismatch)`：写 `F0Tg` 偶发该码但值仍生效 → 只认回读。
8. **读写权限在固件层不对称**：读任意进程可读；写受限 key 非 root 被拒。
   每键属性字节：bit7=可读、bit6=可写、bit0=私有写（风扇控制键多为 `0xC0`/`0xC1`）。
9. **错误码**：`0x82 SmcBadCommand`（Mode 3 拒绝手动写）、`0x84 SmcNotFound`（键不存在，可用于探测）、
   `0x87 SmcKeySizeMismatch`、`0x89`（未预置 dataSize 时读值失败）。
