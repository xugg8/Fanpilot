## 0. 一句话结论

**架构方向是对的（控制层 / 特权层 / 硬件层分层、退出即恢复、CLI+菜单栏双形态都要保留）**，
但有 **3 处必须改的设计、2 处会直接踩坑的实现细节、1 处被实测推翻的核心假设**：

| 项 | 原计划 | 实测结论 | 处置 |
|---|---|---|---|
| 核心假设 | "日常满载压到 92°C 以下问题不大" | ❌ **纯 CPU 满载 16 秒就到 112°C**，Apple 曲线前 14 秒风扇还在最低转速 | 承诺改为"**抢跑式压峰**"并分级承诺（§2） |
| 主控算法 | 自适应曲线 + PID | ⚠️ PID 必然滞后（热时间常数 15-30s + 风扇爬升数十秒） | 改为 **前馈(功率) + PI(稳态) + 迟滞/速率限制**（§4） |
| 权威信号 | 核心温度 | ✅ 但 `Tp*` 单键噪声达 **32°C** | 加 **SensorHub 稳健聚合层**（§3.1） |
| 隐藏信号 | 未提及 | ✅ **`PDTR` 免 root 可读系统功率，2 秒内响应**（27W→88W） | 作为前馈主输入（§4.2） |
| 阈值设计 | 92°C 拉满 / 95°C 接管 | ⚠️ 本机正常负载就 110°C+，会变成"每次编译都告警" | 阈值分族分档 + 瞬态/持续区分（§4.4） |
| 传感器选取 | 全部温度键取最大值 | ❌ **`Tf06/16/26/36/46` 恒定 97-116°C** → 风扇会永久 100% | 强制排除表（§3.2） |
| 写入校验 | 未提及 | ❌ **非 root 写被内核以 `kIOReturnNotPrivileged` 拒绝**，但输出缓冲区全 0 → `result` 读作 "成功" | **先查 kern_return、再回读校验**（§3.3） |
| 特权方案 | SMAppService + 自签 | ⚠️ 自签无 Team ID，SMAppService 注册易卡在放行环节 | **先用 sudo LaunchDaemon**，SMAppService 后置为打包升级项（§6） |
| P0 方法 | 参考社区键表 | ⚠️ 社区键表不覆盖 M4 Max 且含假键 | 改为**差分负载指纹标定**（已完成初版，§7 P0） |
| 键名 | 提到 `F0Sd` | ❌ 本机**无此键** | 用实测键表（详见键位图 §2） |

## 1. 目标与承诺（修订为可测口径）

### 1.1 重新定义 "92°C"

原目标"满载 92°C 以下"在本机需要**分负载类型**承诺，否则第一周就会被真机数据打脸：

| 负载类型 | 实测功耗 | 实测温度（Apple 曲线） | 抢跑式满转速下**预期** | 承诺口径 |
|---|---|---|---|---|
| CPU-only 编译/渲染 | ~88-90W | 112°C | 估算 70–85°C ✅ | **承诺 ≤92°C 稳态** |
| GPU-only 渲染/AI | 60-100W | 100–110°C | 估计 80–95°C ⚠️ | 承诺"压峰"，实测后定 |
| CPU+GPU 双满载 | 120-150W | 112–115°C | 可能仍 >95°C ❌ | **不承诺 92°C**，承诺"最快拉满 + 告警 + 如实记录" |
| 内存带宽型 AI（本地大模型） | 100W+ | 112.8°C | 同上 ⚠️ | 同上 |

> 估算依据：Apple 曲线在 112°C 时风扇仅 1749/5777 RPM（30%）；满转速下风量约 2.5–3×，
> 散热热阻显著下降。**这仍是估算，必须由 P5 实测确认，并写进 README。**

### 1.2 真正的价值主张（比"92°C"更站得住脚）

实测已经证明：**慢的不是风扇，是 Apple 的决策**——风扇跟随目标转速的滞后仅 2–4 秒，
而 Apple 的热曲线在负载出现后**前 14 秒死守最低转速**。所以 FanPilot 的立足点是：

1. **抢跑**：用功率信号在负载出现后 **2 秒内**把目标转速拉到合适档位（Apple 要 14-24 秒）；
2. **怠速地板**：空闲时维持一个可配置的最低转速（如 2000–2500 RPM），
   把"风扇从 1350 爬到 5777 需要数十秒"的机械延迟**提前消化掉**；
3. **如实观测**：把温度/转速/功率/策略全程落盘，让"哪种策略真的有效"有据可依。

## 2. 修正后的安全红线（SafetyGuard）

在原 6 条基础上，**新增 4 条**（都是实测逼出来的）：

| # | 规则 | 来源 |
|---|---|---|
| 1 | 转速下限 = `F0Mn`（本机 1350），永不突破 | 原计划 |
| 2 | 关键簇超温 → 目标拉满 `F0Mx`（本机 5777）+ 告警 | 原计划（阈值见 §4.4） |
| 3 | 强制接管 + 通知 | 原计划 |
| 4 | 多传感器联动（CPU/GPU/内存簇任一越限） | 原计划 |
| 5 | 三条恢复路径（正常退出/崩溃/看门狗超时） | 原计划 |
| 6 | 睡眠暂停、唤醒重评 | 原计划 |
| **7** | **每次写入先查 `kern_return`、再回读校验**；任一失败 → 视为失败，重试 3 次后回落到"仅监控"模式并显式告警 | ★ 实测：非 root 写被内核拒（`kIOReturnNotPrivileged`），输出缓冲区全 0 使 `result` 看似为 0 |
| **8** | **helper 每次启动的第一件事是"无条件恢复到系统自动"**，然后再读状态、再应用策略 | ★ 崩溃后 launchd 重启场景下，这是唯一可靠的复位点 |
| **9** | **写路径与安全判断分离**：写入由单一串行执行器串行化；安全判断独立线程，可随时抢占下发"拉满/复位" | ★ 避免控制环与安全环互相阻塞 |
| **10** | **强制模式必须有心跳**：helper 记录 armed 时间戳，launchd 看门狗超过 N 秒未心跳 → 恢复自动 | ★ 防"进程被杀但 `F0Md` 仍为强制" |

**红线纪律（写进代码注释与 README）**：
- 绝不做任何"绕过 `F0Mn` 下限"的优化；
- 绝不在未回读校验的情况下宣称"已接管"；
- UI 必须实时显示"当前是否真的在强制模式"（回读值），而不是"我们以为的"状态。

## 3. 架构（修订版）

```
交互层   Menu Bar App (SwiftUI)        CLI (fanpilot)
              │  XPC（订阅推送）            │  XPC / 直连（CLI 可免 App 独立跑）
控制层   ┌─────────────────────────────────────────────┐
         │ ControlEngine                               │
         │  ├ FeedForward   ← PDTR 功率 / GPU 利用率    │  ★ 新增：抢跑
         │  ├ Feedback(PI)  ← SensorHub 稳健温度        │
         │  ├ Shaper        ← 迟滞 + 速率限制 + 地板     │  ★ 新增：防震荡/防噪声
         │  └ CurveTable    ← 预设/自定义曲线/固定 RPM   │
         ├ SafetyGuard（独立线程，可抢占）                │
         │  ├ Threshold 分族分档  ├ Alarm  ├ Watchdog    │
         ├ SensorHub（唯一 SMC 读取者）★ 新增            │
         │  ├ KeyRegistry（有效键表 + 排除表）           │
         │  ├ Aggregator（中位数/p90 + 陈旧值剔除）      │
         │  └ PowerTap（PDTR / PHPS）                    │
         └ Actuator（唯一 SMC 写入者）★ 新增             │
            └ WriteVerify（写后回读 + 重试 + 降级）      │
              │                                         │
特权层   PrivilegedHelper（root，LaunchDaemon）          │
         └ 复用 ControlEngine；App 仅通过 XPC 下发策略   │
              │                                         │
硬件层   AppleSMC（读：免 root；写：需 root）            │
```

**关键分层原则**：
- **SensorHub 与 Actuator 都只存在于 helper 内**，App/CLI 不直接读 SMC（避免多进程争抢 SMC 通道、
  也让"谁能写"只有一个入口）。
- App 崩溃不影响 helper；helper 崩溃由 launchd 拉起并**自动复位到 auto**（红线 #8）。

### 3.1 SensorHub：稳健聚合（解决 `Tp*` 32°C 噪声）

```swift
struct SensorReading { let key: String; let raw: Float; let age: Duration }

// 1) 采样：每簇读全部键，2 Hz，单连接串行
// 2) 剔除：与同簇中位数偏离 > 15°C 的样本判为陈旧/多路复用残留，丢弃
// 3) 聚合：
//      cpuHot  = p90(剔除后的 Tp 簇)      // 用分位数而非 max，避免单点毛刺触发误动作
//      gpuHot  = p90(Tg 簇)
//      memHot  = p90(TCM/TCD/TVV 簇)
//      power   = PDTR (W)
// 4) 决策附加条件：越限必须**连续 2 个采样点**成立才动作（约 1 秒）
```
> 实测依据：`Tpx5` 4 次采样波动 32.3°C；冷却期 `Tp` 报过 40.0°C 而邻居 83–84°C。
> 稳定键（`TCMz` 波动 0.92°C、`TCMb` 0.66°C）用于交叉校验。

### 3.2 KeyRegistry：启动标定 + 强制排除

- **启动自检**（1 次，约 5 秒）：枚举全部键 → 记录 dtype/size；
  对温度键做 3 轮采样，标记 `stable` / `noisy` / `frozen`。
- **强制排除表**（本机实测，硬编码为已知坏键 + 运行时自动追加 frozen 键）：
  `Tf06 Tf16 Tf26 Tf36 Tf46 TVMX TVMx TVmS TVms TVxx TVMD TVmd Ta01 Ta05 Ta09 Ta0L Ta0P Ta0S`
- **不入控制环但可用于展示**：电池(`TB*`)、环境(`Ta*`)。
- 配置化：`sensor-profile.json` 允许用户/后续版本覆盖，便于 macOS 升级后维护（风险 §8）。

### 3.3 Actuator：唯一写入口 + 写后回读校验（**本方案最重要的一处新增**）

```swift
func setTargetRPM(_ rpm: Float) throws {
    let clamped = min(max(rpm, fanMin), fanMax)          // 红线 #1：永不低于 F0Mn
    try write(key: "F0Tg", type: .float, value: clamped)
    let readBack = try readFloat("F0Tg")
    guard abs(readBack - clamped) < 25 else { throw .writeRejected }   // ★ 校验
    // 连续 3 次失败 → 进入 monitorOnly 模式 + 醒目告警（红线 #7）
}

func engageForcedMode() throws {
    try write(key: "F0Md", type: .uint8, value: 1)       // ★ 注意是 ui8，1 字节
    guard try readUInt8("F0Md") == 1 else { throw .writeRejected }
}
```
> 实测依据：`F0Md` 是 `ui8`（1 字节）；把 float 写进去必然失败；
> 且**非 root 时内核返回 `kIOReturnNotPrivileged`（0xE00002C1）、输出缓冲区全 0**，`result` 读作 0x00 形似成功。
> **类型必须取自 `KEYINFO`，不许硬编码；写入必须两步校验（kern_return + 回读）。**
### 3.4 时序与性能预算

| 项 | 目标 | 说明 |
|---|---|---|
| 温度/功率采样 | **2 Hz** | SMC 单连接串行；读 ~100 键约 50ms |
| 控制环 | 2 Hz | 与采样同拍 |
| UI 刷新 | 1 Hz | 走 XPC 推送，App 不读 SMC |
| 内存 | **<50MB** | SwiftUI 菜单栏 App 常态 30–60MB；避免缓存全量 3386 键（只留 ~300 温度的 registry） |
| 日志 | 1 Hz CSV | 字段与 `thermal_daylog` 对齐（见 §9） |

## 4. 控制器设计（替换"PID 自适应曲线"）

### 4.1 为什么不能只用 PID

实测的物理链路：**负载变化 → 功率立即变化(2s) → 核心温度上升(16s 到 +38°C) → 风扇爬升(数十秒)**。
被控对象的纯滞后 ≈ 15–30 秒，而执行器满行程需要数十秒。纯 PID 在这种对象上要么振荡、
要么必须把增益压得极低（响应更慢）。**正解：用功率做前馈提前动作，PID 只修稳态残差。**

### 4.2 前馈（FeedForward）—— 抢跑的核心

实测映射（本机，10 核满载 ≈ 88W，闲置 ≈ 27W）：

| `PDTR` 功率 | 建议基础目标转速 | 说明 |
|---|---|---|
| < 35W | `F0Mn`（1350）或"怠速地板"（可配 2000–2500） | 闲置；地板用于换取抢跑余量 |
| 35–55W | ~2500 RPM | 轻度负载 |
| 55–75W | ~3800 RPM | 中度负载 |
| 75–95W | **5777 RPM（拉满）** | 满载，直接拉满而不是等温度 |

**阶跃规则（抢跑）**：若 `PDTR` 在 2 个采样点内上升 > 15W → **立即跳到上表对应档位**（不等温度）。
> 实测价值：Apple 在负载后 14 秒仍停在 1350 RPM；FanPilot 可在 **2 秒内**拉到 3800–5777。

### 4.3 反馈（PI）+ 整形（Shaper）

- 误差 `e = targetTemp - hotSpot`（`hotSpot = max(cpuHot, gpuHot)`）
- `P` 项：`Kp = 25 RPM/°C`（可配）
- `I` 项：慢积分，`Ki` 极小（如 1 RPM/(°C·s)），**带抗积分饱和**
- **迟滞**：±3°C 死区，避免在阈值附近抖动
- **速率限制（防震荡/防噪音突变）**：目标上调 ≤ 800 RPM/s，下调 ≤ 300 RPM/s（非对称：快升慢降）
- **怠速地板**：`target = max(target, floorRPM)`，`floorRPM` 默认可关，开启时 2000–2500 RPM

### 4.4 阈值分族分档（替换"92/95 一刀切"）

| 触发条件（连续 2 点成立） | 动作 | 说明 |
|---|---|---|
| `cpuHot ≥ 88` 且 `power ≥ 60W` | 目标提到 85% 上限 | 正常高负载，静默处理（**不告警**） |
| `cpuHot ≥ 95` 或 `gpuHot ≥ 95` | 目标拉满 + 记录事件 | 仍然不弹告警，只记日志 |
| `cpuHot ≥ 100` 持续 > 10s | 目标拉满 + **通知** | 这是"真实高温"，值得打扰用户 |
| `cpuHot ≥ 105` 持续 > 5s | 拉满 + 告警 + 建议降负载 | 接近平台极限 |
| 任一关键簇 **2 秒内跳升 > 25°C** | 立即拉满（前馈兜底） | 突加载荷的特征 |
| 传感器簇读数**相互矛盾**（如某键离线/全簇 frozen） | 进入保守模式（拉满）+ 告警 | 传感器失效保护 |

> 实测依据：本机 10 核满载稳定在 110–112°C，GPU/内存型负载峰值 112.8°C。
> 若按"92°C 就告警"，用户一天会被打扰几十次 → 告警必然被关掉，安全机制形同虚设。
> **告警必须稀有才有价值。**

## 5. 与 macOS 热管理的边界（重要，原计划未覆盖）

1. **写 `F0Md=1` 等于接管风扇**：macOS 不再用风扇参与热管理，只剩降频（DVFS）这一手。
   这意味着"压住温度"的责任转移到本软件 —— 而**降频仍会先于本软件发生**（与原计划的诚实预期一致）。
2. **不要与系统互抢**：若保持 `F0Md=0` 而只写 `F0Tg`，系统会立刻覆盖（实测无效）。
   所以"温和干预"这条路走不通 —— 要么接管，要么不接管。**UI 必须如实表达这一点。**
3. **强制模式下的失败态**：软件挂掉时风扇会停在最后写入的目标值。缓解：
   - 红线 #8/#10（启动即复位 + 心跳看门狗）
   - **失败时宁高勿低**：异常路径的目标值取"当前值"而非 `F0Mn`（宁可吵一点，不要热）
4. **重启语义**：SMC 强制状态在重启后是否复位需在 P1 实测确认（写进 `Docs/` 并注明结论）。

## 6. 特权与签名（P3 的**降险**方案）

| 方案 | 可靠性 | 成本 | 建议 |
|---|---|---|---|
| **A. `sudo` 安装 root LaunchDaemon**（`/Library/LaunchDaemons/com.x.fanpilot.helper.plist`） | ★★★★★ 100% 可控、可脚本化、可测 | 需一次 `sudo`（与"首次手动放行"的既定决策一致） | **P1/P3 首选，先跑通功能** |
| B. SMAppService（`SMAppService.daemon`） | ⚠️ 自签无 Team ID 时易卡在系统设置放行；需 App 与 helper 签名一致 | 中 | **P4 作为打包升级项**，与"Developer ID 升级开关"并列，feature flag 控制 |
| C. SMJobBless | 中（已弃用） | 中 | 不推荐用于新项目 |

**结论**：把 A 作为默认交付路径，B 只在检测到 Developer ID 签名时启用。
这样 P1/P2 不被签名问题阻塞 —— 这是原计划最大的排期风险点。

## 11. 实测补充：GPU 负载相（2026-09-11，指纹标定结果）

用**控制变量加热**（GPU-only / 内存带宽-only）跑出的关键事实，全部落盘在 `Docs/sensor-profile.json`：

### 11.1 三种负载的功耗等级（`PDTR` 实测）

| 负载 | 峰值功率 | 稳态 | 说明 |
|---|---|---|---|
| 闲置 | 24–28W | — | 风扇常处于**停转**或最低 1350 RPM |
| CPU-only（10 线程满载） | **88W** | 88–90W | `Tp` 16 秒内 74→112°C |
| GPU-only（MPS matmul） | **136W** | 118–126W | `Tg` 25 秒到 100.7°C |
| 内存带宽型 | 88–91W | 90W | `Tp` 上升最明显（+33°C） |

**结论**：GPU 负载的功耗等级比 CPU 高 **55%**，是这台机器最热的场景 —— 也解释了为什么本地视频生成会冲到 112°C。

### 11.2 关键发现：**GPU 负载下最热的传感器不是 CPU**

| 传感器族 | 基线 | GPU 负载后 | Δ | 内存负载后 | Δ |
|---|---|---|---|---|---|
| `Tg`（GPU 簇） | 49.9 | 99.5 | **+49.6** | 64.9 | +15.0 |
| `Tf4` / `Tf3` | 49.9 / 51.5 | 98.1 / 96.5 | +48 / +45 | 81.2 / 72.7 | +31 / +21 |
| `TVD`（供电） | 60.4 | 106.7 | **+46.3** | 87.8 | +27.4 |
| `TVM` | 54.0 | 97.3 | +43.3 | 75.9 | +21.9 |
| **`Tp`（CPU 核）** | 50.5 | **83.0** | **+32.5** | 83.4 | +32.9 |
| `TCM`（内存） | 75.5 | 106.7 | +31.2 | 94.7 | +19.2 |
| `TB0`/`Ta0`（电池/环境） | 30 / 8.6 | 30 / 8.6 | **0** | 30.3 / 8.6 | 0 |

**结论**：GPU 负载下 `Tp` 只升到 83°C，而 GPU 簇到 99.5°C、供电到 106.7°C。
**只盯 CPU 温度的控制器对 GPU 负载几乎无感** —— 分族阈值（§4.4）不是可选项，是必需项。
单键层面最敏感的是 `Tf24/Tf28/Tf29/Tf19`（+59°C）与 `TCDX`/`TVV0`（+56.7°C）。

### 11.3 Apple 曲线的滞后有多严重（136W GPU 负载全程）

| 时刻 | PDTR | Tg | TVV（供电） | 风扇目标 | 实际 RPM |
|---|---|---|---|---|---|
| 0s | 25.0W | 49.6 | 53.4 | 1350 | 1352 |
| +5s | **135.9W** | 85.5 | 96.5 | 1350 | 1343 |
| +10s | 135.7W | 89.8 | 101.1 | 1350 | 1349 |
| +15s | 135.3W | 96.0 | 105.1 | 1350 | 1345 |
| +20s | 133.3W | 99.3 | 108.7 | 1514 | 1485 |
| +30s | 121.5W | 100.5 | 109.4 | 1984 | 1950 |
| +46s | 124.3W | 100.0 | 111.7 | 2686 | 2678 |
| +70s | 118.5W | 99 | 110 | 3235 | **3235（仅 56%）** |

**这是 FanPilot 存在意义的最终证据**：136W 负载持续 70 秒，Apple 的曲线只把风扇推到 **56%**，
而供电温度已经 111.7°C。**风扇上限 5777 RPM 中，有 44% 的散热能力在这整段时间里没被使用。**

## 12. 重大更新：M4 Max MacBook 的风扇锁与解锁序列（2026-09-11）

本轮 root 实测 + 对照公开逆向调研（`agoodkind/macos-smc-fan`，经 `leaperone/smctl` 整理；
**均属逆向结论，本方案只采用能在本机复现的部分**）修正了三条关键设计。

### 12.1 `F%dMd` 模式语义（本机已复现）

| 值 | 含义 | 本机观测 |
|---|---|---|
| 0 | **auto**（系统管理） | 机器偏热、风扇在转时读到 0 |
| 1 | **manual**（本软件接管） | 需解锁后才能写入 |
| 3 | **system**（AppleCLPC 缓解态） | **风扇停转（低温闲置）时读到 3** |

**关键**：Mode 3 不是"自动的另一种写法"，而是固件在缓解态下**拒绝手动写入**的状态。
我们首轮 root 测试失败（写 `F0Md=1` 后回读仍是 3）正是撞在这个锁上，**不是权限问题**
（euid=0 时内核已接受调用，不再返回 `kIOReturnNotPrivileged`）。

### 12.2 本机键表探测结果（运行时探测，不维护芯片表）

| 键 | 存在性 | 类型 | 当前值 |
|---|---|---|---|
| `F0Md` / `F1Md` | ✅ 存在 | ui8 | 3（停转时）/ 0（运行中） |
| `F0md` / `F1md`（小写） | ❌ 不存在 | — | M5 才用小写，探测逻辑已兼容 |
| **`Ftst`** | ✅ **存在** | ui8 | 0 ← **解锁闸门** |
| `FS! ` | ❌ 不存在 | — | Intel 时代的强制手动键 |
| `F0Tg`/`F0Ac`/`F0Mn`/`F0Mx` | ✅ | flt | 0 / 0 / 1350 / 5777 |

→ 本机属"M4 Max MacBook 形态"：**存在 `Ftst`，需要两阶段解锁**。

### 12.3 两阶段解锁序列（已实现于 `FanActuator.unlockManual()`）

```
阶段 1  直写 F0Md = 1
        ├─ 沉降窗口内回读到 1 → 完成（M1/M5 等无锁定机型走这条）
        └─ 仍是 3 → 进入阶段 2
阶段 2  写 Ftst = 1
        等 0.5s
        在 10s 内以 0.1s 间隔重试 F0Md = 1（每次带 6×200ms 沉降校验）
        调研实测：写 Ftst 后约 3–4s F0Md 变 0，重试成功通常 4–6.5s
```

### 12.4 ⚠️ SMC 写入**异步生效**（本机必测项，已写进实现）

调研的真机记录明确：**写完立即回读返回旧值，新值要数百毫秒后才可见**
（`写 F0Tg=2500 → 立即读 = 1000（旧）→ 1s 后读 = 2500`）。

后果：**"写后立即回读校验"会必然误报失败**，而"已解锁但上层以为失败"会留下
**无主手动态**（风扇被接管但没人负责）—— 比单纯失败更危险。

→ `FanActuator.WritePolicy` 已实现沉降窗口：**最多回读 6 次、间隔 200ms（≈1.2s）**，
仍不匹配才计为失败。单元测试 `testVerificationToleratesAsynchronousApply` 覆盖。

> 这条也解释了我们第一轮"回读 3.0 → 判定失败"的观测：既有 Mode 3 锁，
> 也有回读过早的成分，两者叠加。

### 12.5 ⚠️ thermalmonitord 会持续 reclaim —— 必须常驻 + 重断言

- 只要 `Ftst≠1`，系统就在数秒内把模式抢回 3；轮询频率**随负载变化**：
  空闲约 4000ms，**高负载下可快到 250ms**。
- 控制进程一退出，几秒内手动控制即失效。
- **架构结论**：P3 的 helper 必须是**常驻进程**，并且控制环要**周期重断言**
  （写模式 + 写目标），而不是"设一次就完事"。`FanActuator.reassert()` 已实现。
- **有利的一面**：reclaim 本身就是 Apple 设计的崩溃兜底——软件挂掉后系统会自动接管，
  所以"降级为系统控制"天然安全。这让我们的 fail-safe 设计更容易成立。

### 12.6 恢复自动的正确顺序（容易写错的点）

1. 先把**所有**风扇的模式写回（原值）
2. **仅当**没有其它风扇仍处于 manual 时，才把 `Ftst` 写回 0（且当前为 1 才写，幂等）
   —— `Ftst` 是**全局闸门**，提前关掉会让还在手动的风扇被系统抢走

`FanActuator.releaseToAuto()` 已按此顺序实现，测试 `testReleaseOrderModeBeforeFtst` 断言顺序。

### 12.7 其它可用信息

- `F%dTg` **不受 min/max 约束**，理论上可设 0（停转）。我们的"不低于 `F%dMn`"是
  **产品层的安全策略**，不是硬件限制 —— 保持这条红线不变。
- `result=0x87 (SmcKeySizeMismatch)` 在写 `F0Tg` 时会偶发，**但值仍生效** → 校验只认回读。
- 特权 helper 若走 `SMAppService` 注册，需 **Developer ID 签名（付费账号）**；
  这**再次确认了我们选 `sudo` 安装 LaunchDaemon 的路线是对的**（自签即可用）。

### 13.2 抓到的 bug：`auto` 谎报成功（已修 + 回归测试）

**现象**：`fanpilot auto` 打印"✅ 已恢复系统自动控制"，但 `F0Md` 仍是 **1（manual）**。

**根因**：`releaseToAuto()` 恢复的是"**构造时读到的原始模式**"。而 CLI 每次调用都是**新进程**
——`auto` 这个进程构造时读到的"原值"正是上一条命令留下的 **1**，于是它"忠实地"把
手动模式又写了一遍；而校验比对的也是同一个错误目标，所以还报告成功。

**这类 bug 的性质**：不是崩溃，而是**"以为安全、实际不是"** ——
用户以为风扇已交还系统，实际上是一个已经退出的进程留下的手动态在维持。

**修复**：
- `releaseToAuto(target:)` 改为**显式目标模式**，默认 **0 = 系统自动**；
  只有"本进程确实接管过"且调用方明确要求还原时，才使用 `originalMode`。
- 增加**诚实性检查**：恢复后只要还有风扇处于 manual，就返回失败并给出错误。
- CLI 行为调整：`set` **默认会在验证后自动恢复**（安全默认），
  需要保持手动必须显式 `--hold`（并打印醒目警告）；新增 `fanpilot mode <0|1>` 用于诊断。
- 新增 2 项回归测试（现共 **18 项全绿**）：
  `testAutoOnFreshProcessGoesToZeroNotBackToManual`（正是这个 bug）、
  `testReleaseReportsFailureIfStillManual`。

### 13.3 修正：风扇本身很快，"数十秒爬升"是错的

上一轮我曾根据 Apple 曲线的表现推断"风扇机械爬升需要数十秒，所以需要怠速地板"。
**实测推翻**：手动下发 4000 RPM 后，**2 秒内实际转速即到 3891 RPM**（≥1270 RPM/s）。

连带修正：
- 慢的**始终是 Apple 的决策**（负载后 14–18s 风扇目标才动），不是风扇硬件。
- **"怠速地板"从必需项降级为可选项**（仍有降噪/降温收益，但不再是抢跑的前提）。
- 前馈控制的窗口非常宽裕：负载出现后 2 秒内下发目标，风扇 2 秒内到位，
  而温度需要 16 秒才到峰值 —— **抢跑完全来得及**。

### 13.4 reclaim 的真实时序（重要修正）

- 调研称"控制进程退出后几秒内 `F0Md` 从 1 → 3"。
- **本机实测**：进程退出后 **12 秒内模式仍为 1**（脚本第 5 步观测窗口）；
  但**数分钟后复查，模式已回到 3（system）、风扇停转**。
- **结论**：
  1. reclaim **确实存在，但有明显延迟**，且很可能与热状态/空闲有关（高负载下应更快）；
  2. **不能依赖它做"及时"恢复** —— helper 必须自己负责收尾（红线 #8/#10 保持不变）；
  3. 但**系统最终会兜底**，这对硬件安全是利好：软件彻底挂掉也不会永远锁死风扇。
- 待补：高负载下退出进程，测 reclaim 是否变快（对应调研的 250ms fast mode）。

### 14.2 关键发现：`F0Md = 0` **不代表锁已释放**

本次脚本前置门禁读到 **`起始 F0Md = 0`**，于是判定"非锁定态、走直写路径"；
但实测**直写依然失败**（回读 0），必须回退到 Ftst 分支：

```
F0 直写 mode=1 未生效（回读 0）→ 判定为 Mode 3 锁定
已写 Ftst=1，等待 0.5s 后重试 mode=1
Ftst 解锁：重试 1 轮 → 成功
```

**推论**：`F0Md` 的读数值只是"上报状态"，不能当作"手动写入是否被允许"的判据 ——
**必须始终按两阶段尝试**（先直写、失败再 Ftst）。我们最初的设计恰好如此，
这次被真机数据证明是**必要**而非冗余。

> 反面教训：若按"读到 0 就认为能直接写"来做分支优化，会在这类过渡态下直接失败。

### 15.3 模拟（`fanpilot plan`）暴露并修掉的两个设计问题

做 `plan` 模拟的价值立刻体现出来了 —— 它抓出两个只有"跑一遍看结果"才会发现的错误：

**① 回放时间基准不一致 → 速率限制把转速"锁死"**
`seed()` 默认用真实时钟，而回放用相对时间戳，导致 dt ≈ 0、允许变化 ≈ 0
（2 秒时该到 4269 却停在 1352）。→ `seedFromCurrentRPM(_:now:)` 支持显式时间基准。

**② PI 的负修正与大功率前馈互相打架（→ 改为非对称限幅）**
GPU 136W 但温度还凉（60°C）时，PI 把目标从 5777 拉回 **4277** ——
而热惯性决定"现在凉"不代表"马上不热"（功率到位后要 16 秒温度才到峰值）。
→ 修正量改为 **非对称**：正向足额（+1500），**负向限幅（−600）**。
修正后同一格变成 5177，既不再自我拆台，又保留了"确实凉可以降一点"的能力。

### 15.4 速率限制的一次修正

初版 `slewUpRPMps = 800`，回放显示它**拖慢了抢跑**：2 秒只允许升 1600 RPM。
但实测风扇本身可达 **~1270 RPM/s**，软件不该比硬件更慢。
→ 升速上限提到 **1500 RPM/s**（略高于硬件，等于不额外限制），
降速保持 300 RPM/s（避免忽高忽低的听感）。**防振荡改由 PI 死区 + 最小保持时间负责。**

### 15.5 测试覆盖（31 项，其中控制相关 12 项）
