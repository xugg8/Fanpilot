## 2. 前馈映射（清凉档）—— 本档"抢跑"的核心

锚点直接来自实测功耗等级：**闲置 24–28W / CPU 满载 88W / GPU 满载 118–136W**。

| PDTR 功率 | 前馈转速 | 说明 |
|---|---|---|
| ≤ 30W | 1350 | 闲置（= 硬件下限） |
| 45W | 1900 | 轻负载 |
| 60W | 2600 | 中负载 |
| 75W | 3400 | |
| 90W | 4200 | ≈ CPU 满载 |
| 110W | 5000 | |
| ≥ 130W | 5777 | ≈ GPU 满载 → 满速 |

**为什么前馈故意"保守起步"**：一上来就满速太吵。前馈给出合理起点，**由 PI 按实际温度补足**——
闭环仍然会在需要时拉到满速（见 §4 回放）。

## 4. 与 Apple 原厂曲线的对比（真机实测时序回放）

### CPU-only 满载（10 线程，实测 88W）

| 时刻 | PDTR | 热点 | **本策略** | Apple 原厂（实测） |
|---|---|---|---|---|
| 0s | 28W | 74°C | 1350 | 1319 |
| **2s** | 85W | 96°C | **4269** | 1355 |
| 8s | 87W | 101°C | 5777 | 1380 |
| 14s | 88W | 106°C | 5777 | 1340 |
| 24s | 88W | **112°C** | 5777 | 1702 |

**Apple 在这 24 秒里几乎一直把风扇压在最低转速，温度因此冲到 112°C。**
本策略在功率到位的第 2 秒就把转速抬到 4269，第 8 秒满速 —— 这是"抢跑"的全部意义。

### GPU 满载（MPS，实测峰值 136W）

| 时刻 | PDTR | 热点 | **本策略** | Apple 原厂（实测） |
|---|---|---|---|---|
| 0s | 25W | 53°C | 1350 | 1352 |

| 15s | 135W | 105°C | 5777 | 1345 |

## 5. 安全守护（优先级高于任何档位）

| 条件（分族：CPU / GPU / 内存 / 供电任一达到即触发） | 动作 | 是否打扰用户 |
|---|---|---|
| ≥ 88°C | 静默提高转速（记录事件） | ❌ 不打扰 |
| ≥ 95°C **连续 2 点** | 目标拉满 5777 | ❌ 不打扰 |
| ≥ 100°C 持续 10s | 拉满 + **通知** | ✅ |
| ≥ 105°C 持续 5s | 拉满 + **告警**（建议降负载） | ✅ |
| 2.5s 内跳升 ≥ 25°C | 立即拉满（前馈兜底） | ❌ |
| 关键温度族失明 | 保守拉满 / 交还系统 | ✅ |

**为什么阈值这么高**：本机 CPU-only 满载稳定 110–112°C、GPU 峰值 112.8°C，
Apple Silicon 结温规格约 110°C。按 92°C 告警会变成"每次编译都弹窗"，
用户一周内就会把告警关掉 —— **告警必须稀有才有价值**。

**与 §1.1 承诺口径的关系**：88°C 目标是"日常编译/渲染"的承诺；CPU+GPU 双满载时
PI 会饱和到满速，此时只能承诺"压峰 + 如实记录"，不承诺 92°C。

## 7. 已知取舍与未验证项（诚实清单）

**取舍**
1. **噪音 vs 温度**：本策略明显比 Apple 激进 —— 第 2 秒就到 4269 RPM，会有明显风声。
   这是"压住 112°C"必须付的代价。若你更在意安静，把 §6 的"更静"档调上。
2. **最强清凉档的 2500 RPM 怠速地板**意味着**空闲时风扇也不停**（Apple 在低温时会停转），
   会有持续的低频噪音。这是刻意换"随时待命的抢跑余量"。
3. **接管期间 macOS 不再用风扇参与热管理**（只剩降频）。实测 reclaim 有延迟，
   所以本软件必须自己负责收尾 —— 已用死人开关 + 退出交还 + 失明交还三层兜底。

**未验证（P5 烤机才能定）**
- [ ] 88°C 目标在 **CPU-only 满载**下能否真正守住（估算可达，需实测）
- [ ] **GPU 满载 136W** 下满速能压到多少度（估计 85–95°C，可能守不住 88）
- [ ] 前馈锚点是否需要按实测再上移
- [ ] 稳态下转速是否真的不振荡（当前靠死区 + 保持时间，需长时观测）
- [ ] 与其它风扇软件（Macs Fan Control 等）共存时会互相抢控制权 —— 已知互斥

# v1.1 修订（2026-09-11，按你的四点反馈）

## ① 什么时候才激发？——「日常工作不自动激发」已落实

新增**激发策略**（`ActivationPolicy`），默认行为：

| | 条件 | 动作 |
|---|---|---|
| **不接管** | 功率 < 55W **且** 热点 < 85°C | 系统自动，本软件只监控（**风扇不转/不加速**） |
| **接管** | 功率 ≥ 55W **或** 热点 ≥ 85°C，**持续 2 秒** | 接管风扇（去抖，避免一瞬间峰值就拉风扇） |
| **交还** | 功率 < 35W **且** 热点 < 70°C，**持续 30 秒** | 交还系统（含 `Ftst` 复位） |
| **安全例外** | 任一关键簇 ≥ 95°C（连续 2 点） | **无视上面策略直接接管**（此时我们的满速比 Apple 曲线更凉） |

`fanpilot plan` 会打印一天场景的接管/交还时刻：

```
   时刻      场景                        功率   温度   状态
       0s   开机空闲（后台同步）    27W   55°C  ○ 系统自动（监控中）
     182s   编译/导出（真负载）    88W   84°C  ⚡️ 接管风扇
            └ 激发：功率 88W ≥ 55W 持续 2.0s
     390s   回到空闲    26W   52°C  ○ 系统自动（监控中）
```

即：**浏览、文档、听歌、看视频这类日常使用，FanPilot 完全不介入**；
只有编译/渲染/AI 推理这类真负载才接管，负载结束后自动还回去。

> 参考：日常轻负载实测约 40–50W、60–70°C；编译 88W；GPU 推理 118–136W。

## ② 空闲 2500 RPM 已取消（你说得对）

我原来的理由（`预转` 以便抢跑）**被 P1 实测否掉了**：风扇从 1350 到 4000 RPM 只需 **≤2 秒**，
根本不需要预热转速 —— 地板只带来持续噪音，收益为零。现已：
- **所有档位的 `idleFloorRPM` 默认为 nil**（空闲回落至硬件下限 1350，低温时风扇可完全停转）；
- 「最强清凉」档的前馈表起点也从 2500 改回 1350，**"最强"只体现在负载下爬得更快更高**。

## ③ 降频与 Ftst 的关系（**含一处必须澄清的表述矛盾**）

### 先纠正我之前的说法

我先前写过"降频由系统管、与我们完全独立"。这句话**过强了，和后面"`Ftst=1` 会抑制
thermalmonitord 下发温度目标"是自相矛盾的** —— 如果那条路径同时也是降频路径，
那接管风扇就可能让系统的软件层热管理变得不那么主动。以下按证据强度重新表述。

### 三层模型（每层的证据强度不同）

| 层 | 内容 | 谁在管 | 证据强度 |
|---|---|---|---|
| **L1 风扇** | `F%dMd` / `F%dTg`（模式 + 目标转速） | 接管期间 = 本软件 | ✅ 本机实测 |
| **L2 软件层热管理** | `thermalmonitord` → `AppleCLPC` 下发**温度/功耗目标**（与降频相关的闭环） | 系统；但**写 `Ftst=1` 会抑制它的目标断言** | ⚠️ **第三方逆向推断，本机未验证** |
| **L3 固件层保护** | 硬温度上限、紧急降频、过热关机 | RTKit 固件（推测独立于 `Ftst`） | ❓ **纯推断，未验证** |

**因此准确的表述是**：
- **L1 完全归我们**（这也是必须持有 `Ftst=1` 的原因 —— 不写它，固件会用 Mode 3 抢回风扇，
  我们根本无法控制风扇。**`Ftst=1` 不是我们的选择，而是手动控制风扇的入场券**）。
- **L2 是否被我们影响：未知**。`Ftst` 抑制的是 thermalmonitord 的"温度目标断言"，
  而该断言很可能正是它参与热管理的方式。**不能断言"完全独立"。**
- **L3 大概率仍在**（否则 Apple 不会开放 `Ftst` 这个闸门），但**没有实测证据**。

### 那为什么仍然可以接受这个风险？

1. **我们期间的风扇比 Apple 曲线强得多**：实测 Apple 在 110°C 时只给
   3235/5777 RPM，我们给 5777。**实际芯片温度更低才是保护硬件的直接因素**；
2. **`Ftst` 只在真正接管的时段被持有**：任何交还 / 退出 / 异常 / 心跳丢失都会把它复位为 0，
   macOS 立刻恢复**完整**热管理（代码已实现并有测试）；
3. **我们的 SafetyGuard 在接管期间充当风扇侧热管理**（≥95°C 连续两点拉满、105°C 告警）；
4. **可选开关**：`--handback-temp <温度>` 让你在极端温度下**把风扇也交还系统**
   （含 `Ftst=0`），把 L1 也还给 macOS。默认关闭，因为交还会让风扇降速、更热。

### 这个不确定性怎么消除？—— 一个决定性的 A/B 实验（需 root，尚未做）

用**同一固定工作量**分别在两种状态下跑，用 `powermetrics` 采样频率/功耗/热压：

```bash
# A) 系统自动（Ftst=0，Apple 曲线）
sudo powermetrics -i 1000 -n 60 --samplers cpu_power,thermal > /tmp/A.txt &
<同一份基准/编译任务>

# B) 本软件接管（Ftst=1 + 恒定高转速）
sudo fanpilot run --profile fixed --always-on --duration 600 &
sudo powermetrics -i 1000 -n 60 --samplers cpu_power,thermal > /tmp/B.txt &
<同一份基准/编译任务>
```

**判据**：
- 若 **B 在更低温度下完成同样（或更多）工作** → 接管是净收益，L2 的疑点不影响结论；
- 若 **B 温度更低但频率/完成量也更低** → 说明 `Ftst` 确实干扰了系统管理，
  此时应改用 `--handback-temp`（高温交还）或缩短 `Ftst` 持有时间。

**已实测的旁证**：`pmset -g therm` 显示，即使 SoC 到过 **112.8°C**，
macOS **从未记录任何热告警**（`No thermal warning level has been recorded`）——
说明 Apple 自己的"告警"门槛远高于 92°C，也侧面支持我们把通知阈值定在 100°C 的设计。

> ⚠️ 注意：`pmset -g thermlog` 是**实时流**，会一直阻塞终端，不要直接运行；
> 要用请配合 `timeout` 或后台重定向。

## ④ GPU 136W 满载目标改为 95°C（已落实）

新增**重载目标温度**：功率 ≥ 110W 时目标温度自动放宽到 **95°C**；普通负载仍用 88°C。

| 负载 | 目标温度 | 说明 |
|---|---|---|
| 普通（< 110W） | **88°C** | 编译、导出等 |
| 重载（≥ 110W） | **95°C** | GPU 满载/AI 推理 —— 按你的要求"压到 95°C 即可" |

效果（模拟）：136W 且温度 92°C 时，普通负载会继续加转速，重载则允许回落 ——
不再为了够不到的 88°C 一直顶着满速吵人。
